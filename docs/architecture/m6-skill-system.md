# M6 skill system design lock

M6 defines Ocode-owned, versioned method contracts. It does not implement a runtime, install upstream skills, select a skill, plan work, schedule execution, create worktrees, or change M4/M5. The M6.1 executable scope is limited to these contracts and their deterministic validation/projection/qualification support.

## Skill constitution

Ocode owns workflow, roles, constitutional authority, admission, EvidenceRef freshness, provider binding, and execution provenance. A skill is a bounded method contract that states when it applies, what M4 requirements it needs, what result/evidence it promises, and how that exact method becomes qualified. A skill does not grant authority, choose a provider/model, select a role, schedule work, or become a second evidence store.

## Authority, projection, and lifecycle

The authoritative pair is `skills/<id>/protocol.json` and `skills/<id>/SKILL.md`; qualifications are authoritative historical artifacts below the same directory. `protocol.json` owns all fields that machines consume: identity/version, applicability, requirements, structured method skeleton, outputs, evidence/acceptance/failure/stop and qualification requirements. `SKILL.md` owns agent-facing sequencing, cautions, examples, and wording. Every change to either changes the semantic fingerprint and invalidates a prior qualification. No change to either may avoid requalification; qualification descriptions or records do not alter the source fingerprint.

M6.1 will deterministically render `.opencode/skills/<id>/SKILL.md` from canonical `SKILL.md` with a generated provenance header containing skill ID and fingerprint. It will produce a projection manifest containing source/projection fingerprints. Generated runtime files are project-local, ignored, and ephemeral/staged during execution; they are never committed and never accepted as canonical input. A cheap check regenerates to a temporary location and compares manifest/path/content fingerprints; missing, extra, or changed projection is drift and must fail closed before skill execution. Future install/update copies canonical `skills/` and qualification records atomically with the harness release; rollback restores the matching source. It regenerates, never backs up runtime projection as authority.

The lifecycle and its exact QualificationRecord rules are defined in [M6 contracts v1](m6-contracts-v1.md). A record for fingerprint A cannot qualify B. `skill_version` is informative release identity, not a bypass for fingerprint matching.

## M4 and M5 inheritance

For each candidate role, M6 derives the exact `AdmissionRequest` from `SkillProtocol.requirements` as specified in [M6 contracts v1](m6-contracts-v1.md). M4 evaluates role capabilities, constitutional authority, configured-permission projection, reason codes, contract identity, and later effective-subject reconciliation. The candidate role name only selects its manifest-derived contract; no skill ID or `compatible_skills` value can grant it authority or compatibility. This applies equally to operator role listings.

M6 reuses M5 EvidenceRef v1, dependency-scoped freshness, and evidence ladder. It does not define freshness, issue `CURRENT`, use repository SHA as a global freshness gate, or create a second ledger. Skill execution follows exactly: OpenCode JSONL transport → existing `parseOpenCodeEvents()` → existing `extractAssistantModelOutput()` → normalized semantic `model_output` → skill-domain parser → EvidenceCapsule validation. A skill parser never parses raw JSONL. An invalid result gets one precise, bounded correction and is then accepted or fails.

## Legacy state and provenance

`skills/` contains only `.gitkeep`; `.opencode/skills/` does not exist. `agents/manifest.json` has legacy external `compatible_skills` names (`setup-matt-pocock-skills`, `wayfinder`, `grill-with-docs`, `to-spec`, `to-tickets`, `codebase-design`, `diagnosing-bugs`, `prototype`). Agent permissions and `docs/security.md` also mention external skill names. These are advisory-only legacy metadata today: they must not be used by M6 admission, runtime selection, permission authorization, operator explanation, or qualification. A later bounded migration must either remove them or relocate a clearly labeled historical note; M6.0 does not mutate broad agent/config/security content.

The primary upstream source is [Cursor pstack](https://github.com/cursor/plugins/tree/main/pstack), inspected at its actual current path (the prompt’s older `plugins/pstack` URL redirects conceptually but is not the tree path). Its MIT license is copyright Lauren Tan (2026). Pstack supplied concepts only: root-cause-first debugging, explicit evidence/confidence, adversarial review, verification, and context guarding. Ocode rejects Pstack’s model panels, role-to-model mapping, autonomous orchestration, parallelism, task/playbook routing, transcript/memory use, and external-tool ownership because they belong to Ocode’s existing or later layers.

[Matt Pocock’s skills](https://github.com/mattpocock/skills) is a distinct external system, present only because legacy names cite it. It is also MIT (copyright Matt Pocock, 2026), offers its own installation and skill catalog, and is not Pstack. It contributes no adopted M6 contract; the legacy names are neither aliases nor dependencies. No external text/code/SKILL.md is copied, installed, vendored, or made a runtime dependency. Conceptual derivation alone does not require an MIT notice; if a later change copies a substantial portion, it must preserve the relevant MIT copyright/permission notice and attribution.

## Qualification philosophy

Qualification proves that a specific method conforms, not that a prompt looks persuasive or one model produced correct code. Every protocol has: a positive fixture; a method-violation fixture; authority/capability negative fixture; evidence-integrity negative fixture; and context-economy observation. The intended progression is deterministic protocol validation → deterministic fixtures → scarce bounded governed live qualification when required → retained evidence → independent Verifier → adversarial Reviewer → `QUALIFIED`. Fixtures can stub a model result and do not all require live inference. M6.0 performs zero live qualification calls.

Future M6.7 operator surfaces must list/explain skills; show fingerprint/version, requirements, applicability, qualification state/evidence and the explanation for `STALE`/`DISQUALIFIED`; and evaluate candidate roles by deriving M4 AdmissionRequests and rendering their AdmissionDecisions. They must not read `compatible_skills` to answer eligibility.

## M7 consumption boundary

M7 may read a validated canonical protocol, its exact semantic fingerprint, derived lifecycle/QualificationRecord, applicability/non-applicability, M4 requirements, method/output/evidence promise, and ContextCapsule shape. It may ask whether the exact fingerprint is `QUALIFIED`. It may not infer authority from a role name, use legacy compatibility metadata, select a provider, run skills, construct task schedules, or silently requalify changed contracts. Skill selection and Planner Compiler behavior remain out of scope for M6.0.
